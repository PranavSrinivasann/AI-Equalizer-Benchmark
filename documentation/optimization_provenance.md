# Optimization Provenance and Hand-Optimized Comparison

This document answers three questions about the optimized FFE designs:

1. What did each optimized design change relative to its baseline?
2. What is recorded about how the optimized RTL was produced?
3. How much of the improvement would a straightforward hand optimization
   also get, and how much is left over?

All numbers below come from one rebuild with the same tool versions
(`results/rebuild/`, tool versions in `results/rebuild/tool_versions.txt`),
so the designs are compared on equal terms. Reproduce with:

```bash
python3 scripts/rebuild_all.py --seeds 10
```

## 1. How the optimized RTL was produced

The optimized RTL for all three cases was generated by Claude from the
resource-optimization prompt in `prompts/generalization/resource_optimization.txt`
(Cases B and C embed it with their baseline RTL in `case_B_prompt.txt` and
`case_C_prompt.txt`).

| | Case A | Case B | Case C |
|---|---|---|---|
| Model | Claude | Claude | Claude |
| Model version | Not recorded | Not recorded | Not recorded |
| Date | Not recorded | Not recorded | Not recorded |
| Prompt | `resource_optimization.txt`; exact prompt text not saved | `case_B_prompt.txt` | `case_C_prompt.txt` |
| Saved response | Not saved | `results/generalization/case_B/optimized/ai_response.md` | `results/generalization/case_C/optimized/ai_response.md` |
| Iterations | 1 | 1 | 1 |
| Manual RTL edits | None | None | None |

For Cases B and C, the absence of manual edits can be checked directly:
the committed RTL is identical to the RTL in the saved response, apart from
comments. For Case A no response was saved, so this rests on the
experiment log.

The prompt asked for the design to "preserve exactly ... exact saturation
behavior". In Cases B and C the generated RTL removes the saturation logic.
This does not violate that constraint, because saturation can never fire
for those coefficients (Section 3), so the observable behavior is unchanged.

## 2. What changed in each design

### Case A: `[51, -154, 1024, 154, -51]` (antisymmetric outer taps, power-of-two center)

| Change | Effect |
|---|---|
| Pre-adders on the antisymmetric pairs: `x0 - x4` and `x1 - x3` | 5 multiplies become 2 multiplies plus 1 shift |
| Center tap `1024 * x2` written as a concatenation `{x2, 10'b0}` | No multiplier; the comment notes `x2 <<< 10` would silently drop bits |
| Accumulator narrowed to 24 bits (worst case needs 23) | Fewer adder bits |
| Saturation kept, but detected with a sign-bit test (2 XORs + OR) instead of two magnitude comparators | Smaller saturation logic |

Saturation is required here: `sum|c| = 1434 > 1024`, so the output can
reach ±2868 before saturation. The remaining two multiplies (`51` and
`154`) are left as `*` and mapped by synthesis.

### Case B: `[73, -121, 89, 146, -57]` (no symmetry)

| Change | Effect |
|---|---|
| Algebraic regrouping: `acc = 73*S + 16*x2 + 7*B - 64*T`, with `S = x0 + x2 + 2*x3`, `B = x1 + x4`, `T = 2*x1 + x4` | Uses `146 = 2*73`, `89 = 73 + 16`, `-121 = -128 + 7`, `-57 = -64 + 7`; one shared `73*S` replaces three multiplies |
| `73*S = 64*S + 9*S`, `9*S = 8*S + S`, `7*B = 8*B - B` | All multiplies become shift-adds |
| Accumulator narrowed from 28 to 21 bits | Fewer adder bits |
| Saturation removed | Unreachable: output is at most ±972 |
| Output register 11 bits, sign-extended to the 12-bit port | One fewer flop |

### Case C: `[51, -137, 93, 137, -51]` (antisymmetric outer taps)

| Change | Effect |
|---|---|
| Pre-adders: `d04 = x0 - x4`, `d13 = x1 - x3` | 5 taps become 3 terms |
| Factoring: `acc = 3*(17*d04 + 31*x2) - 137*d13` | Uses `51 = 3*17` and `93 = 3*31`; one shared `*3` |
| `17d = 16d + d`, `31x = 32x - x`, `137d = 128d + 8d + d` | All multiplies become shift-adds; 9 adders total |
| Low bits of each shifted operand passed straight through | Adders cover only the bits that can carry |
| Every intermediate sized to its proven range | Fewer adder bits |
| Saturation removed | Unreachable: output is at most ±938 |
| Output register 11 bits | One fewer flop |

## 3. Correctness of the changes

Every design, baseline, optimized and hand-optimized, passes:

- the original 1000-sample regression vectors, and
- 5,693 to 5,765 directed cycles covering power-up and mid-stream reset,
  constant and alternating extreme inputs, worst-case accumulation,
  windows landing exactly on the 12-bit output limits, PAM4 levels and
  5,000 uniform random samples (`testbench/directed/`).

For Case A the directed set produces 322 saturated outputs, so the
saturation path is exercised.

The saturation removal in Cases B and C is safe by a simple bound: with
12-bit inputs, `|acc| <= 2048 * sum|c|`, so the shifted output stays inside
the 12-bit range whenever `sum|c| < 1024`.

| Case | sum\|c\| | Output range before saturation | Saturation reachable? |
|---|---|---|---|
| A | 1434 | [-2868, 2866] | Yes |
| B | 486 | [-972, 971] | No |
| C | 469 | [-938, 937] | No |

`python/verification/check_arithmetic_bounds.py` computes this and also
checks every bit-sliced adder in the Case B and C optimized arithmetic
against exact integer multiplication, over every value each one can see.

## 4. Hand-optimized reference

To separate what any competent hand optimization gets from what the
optimized designs add, each case has a hand-optimized reference in
`rtl/hand/`. It applies only standard, mechanical techniques:

- each coefficient multiply replaced by its canonical signed-digit (CSD)
  shift-add form, one tap at a time;
- the accumulator sized to the worst-case bound;
- saturation removed only where the bound above proves it unreachable
  (B and C), and kept for A.

It deliberately does **not** share terms across taps: no pre-adders on
symmetric pairs, no common factors, no partial-bit adders.

## 5. Results

Logic cells were identical across all 10 placement seeds for every design;
Fmax is the median over 10 seeds, with the range in brackets.

| Case | Design | Logic cells | LUT4 | Fmax, MHz |
|---|---|---|---|---|
| A | Baseline | 638 | 567 | 20.1 [19.3, 20.5] |
| A | Hand CSD | 534 | 467 | 24.4 [22.4, 25.2] |
| A | Optimized | 408 | 350 | 21.3 [20.9, 21.8] |
| B | Baseline | 664 | 582 | 20.3 [19.8, 21.1] |
| B | Hand CSD | 478 | 420 | 27.8 [26.3, 28.7] |
| B | Optimized | 236 | 176 | 35.2 [32.8, 36.1] |
| C | Baseline | 817 | 759 | 26.6 [25.4, 27.6] |
| C | Hand CSD | 527 | 468 | 28.0 [27.2, 29.5] |
| C | Optimized | 247 | 196 | 32.0 [30.3, 32.1] |

Splitting the logic-cell reduction into the part the hand reference gets
and the part only the optimized design gets:

| Case | Baseline → hand | Hand → optimized | Share of total saving beyond hand CSD |
|---|---|---|---|
| A | −104 (−16%) | −126 (−24%) | 55% |
| B | −186 (−28%) | −242 (−51%) | 57% |
| C | −290 (−35%) | −280 (−53%) | 49% |

## 6. Interpretation

- **Area.** Plain CSD shift-add already captures roughly half of the
  logic-cell saving in every case. The other half comes from sharing work
  across taps: pre-adders on antisymmetric pairs (A, C), common factors
  (`73` in B, `3` in C), and adders that skip bits that cannot carry (C).
  These are the techniques a hand designer would have to spot per
  coefficient set, and they are the measurable additional value of the
  optimized RTL here.
- **Case B has no symmetry**, yet it shows the largest gain beyond hand
  CSD (51%). The saving comes from noticing arithmetic relations between
  coefficients (`146 = 2*73`, `89 = 73 + 16`), not from structural symmetry.
- **Timing.** The optimized designs are fastest in B and C. In Case A the
  hand reference is faster (24.4 vs 21.3 MHz) despite using more cells:
  the optimized Case A design leaves its two folded multiplies as `*`,
  which likely synthesize into deeper logic than explicit CSD. Combining the
  Case A pre-adders with CSD multiplies would likely beat both; this has
  not been tested.
- **Scope.** These conclusions cover three fixed coefficient sets on one
  FPGA family and one synthesis flow. The channel-derived coefficient sets
  in the next phase test whether the gains hold for coefficients without
  hand-picked relations.

## 7. Differences from previously recorded numbers

The rebuild uses Yosys 0.70 and nextpnr 0.11.1. Some logic-cell counts
differ from those recorded in `results/generalization/results.csv`:

| Design | Recorded LC | Rebuild LC |
|---|---|---|
| A baseline | 629 | 638 |
| A optimized | 408 | 408 |
| B baseline | 674 | 664 |
| B optimized | 376 | 236 |
| C baseline | 785 | 817 |
| C optimized | 247 | 247 |

The large change for B optimized indicates the earlier result came from a
different tool version or flow; the exact earlier versions were not
recorded. The experiment log also lists 468 logic cells for Case A
optimized, while `results.csv` lists 408; the rebuild reproduces 408.
The comparisons in this document use only the rebuild numbers.
